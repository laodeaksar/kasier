# Kasier Stage Workflow

Use this workflow for staged changes in the Kasier AR Shop repository. It is designed for an owner who is not a programmer: keep explanations simple and preserve the existing work.

## Workflow

1. **Inspect before editing.** Identify the repo, current branch, working-tree changes, remote, and available project instructions. Never overwrite unrelated user changes. Read `AGENTS.md`, `PRD.md`, `ARCHITECTURE.md`, and `TODO.md` completely. Also inspect the relevant `README.md`, `plan.md`, package manifest/lockfile, source, database migrations, and tests. `PRD.md` wins if it conflicts with `ARCHITECTURE.md`; `AGENTS.md` remains the working policy.
2. **Establish the phase gate.** Compare the current implementation and actual test/runtime evidence with the prior-phase outcomes in `TODO.md`. Check required environment-variable *names* without printing values. If a prior phase is missing, broken, or cannot be verified because required configuration is absent, report the evidence and consequences before changing it. Do not silently repair, replace, delete, migrate, seed, or rewrite prior work. Wait for explicit authorization for any database write or prior-phase repair; perform only the operation the user authorized. If the user explicitly directs work to continue despite a known verification gap, preserve that gap and do not invent credentials or data.
3. **Summarize the gate.** Give the owner a concise summary of repository state and understanding (at most 10 lines when requested). Continue only when the prior phase is ready or the user has explicitly authorized proceeding with a stated limitation.
4. **Scope the requested phase.** Read the exact phase clauses in PRD/AGENTS/TODO and the user request. PRD outranks architecture, but the user's current explicit phase request defines what is authorized now. Resolve material ambiguity before implementation. Exclude all later phases and every “future feature.” Do not add libraries, services, or paid dependencies without asking.
5. **Implement in the existing design and structure.** Reuse current conventions and keep business rules in server services, with thin Hono route handlers. Share Valibot schemas between forms and server handlers. Use mobile-first Indonesian UI. Enforce permissions and important rules on the server; hiding controls is only a convenience. Keep credentials in ignored local environment files, never in source, docs, commit, or command output.
6. **For the authorized Kasier Tahap 2 scope,** support a logged-in product list with name, unit, buy price, sell price, and stock; use the already declared TanStack React Table for the table view. Only the owner may create products or change prices, and Hono must enforce this. Cashiers and owners may record stock received; write the receipt and increment stock in one PostgreSQL transaction. The owner-only account page creates cashier accounts through Better Auth; validate with the shared Valibot schema, assign the cashier role server-side, and keep public self-registration disabled. Do not add sales, debts, photos, public catalog, reports, charts, or other later-phase features unless separately authorized.
7. **Keep project records accurate.** Update `TODO.md` with the full acceptance clauses, preserving delivered progress and leaving outcomes unresolved when evidence is incomplete. Keep the route manifest synchronized with real page routes. Update the README with non-programmer steps only when useful. Do not change PRD/architecture contracts without permission.
8. **Validate safely.** Prefer source inspection and existing diagnostics/checks. Run the project's typecheck and build, then focused health/manifest checks where possible. Do not add test dependencies without permission. Do not write sample products, seed users, or other business data to a shared database. State clearly which runtime checks could not be performed because configuration or accounts are missing.
9. **Save to a new branch.** Check whether the proposed remote branch already exists; choose a new name rather than overwrite it. Stage only intended files and explicitly verify `.env`, `.env.local`, credentials, and generated local artifacts are absent. Commit and push only when the user requested saving/pushing or explicitly approved it. Never push to the default branch, force-push, or rewrite history.
10. **Deliver plainly.** In Indonesian, state what is complete, how a non-programmer can try it, what was validated, what remains blocked or needs a decision, and the branch/commit link when available. Do not imply login or database workflows were tested if they were not.

## Kasier project guardrails

- Stack is limited to TanStack React Start, TanStack React Table, TanStack React Store, Formisch + Valibot, Hono, Drizzle, PostgreSQL, Better Auth, DaisyUI, and Tailwind. Reuse locked dependencies.
- Roles are `kasir` and `pemilik`. For Tahap 2, cashiers may view products and record stock receipts, but may not create products, change prices, or manage accounts. Owners may do those owner-only actions. Verify the role on the server for every protected API.
- Stock-receipt history and stock increment must succeed or roll back together. Do not trust browser-only permission checks.
- Project rules require `.env.example` to contain variable names only. If the owner asks for an explained sample, put safe placeholders and comments in a separate `env.template`; never place real values there.
- Keep later-phase areas out of scope: checkout/sales, debt and repayments, product photos, public catalog, receipt printing, analytics/charts, WhatsApp, customer ordering, branches, and barcode features unless the owner later authorizes that phase.
